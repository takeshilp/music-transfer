# API facts (checked 2026-10-27)

What the official docs said when the app was designed. These change often: recheck before relying on them.

## Spotify Web API

- **PKCE**: authorize `GET https://accounts.spotify.com/authorize` with `code_challenge_method=S256`; token `POST https://accounts.spotify.com/api/token` with `client_id` + `code_verifier`, no client secret. Refresh needs only `grant_type=refresh_token`, `refresh_token`, `client_id`; the response may omit a new refresh token (keep the old one). [PKCE flow](https://developer.spotify.com/documentation/web-api/tutorials/code-pkce-flow), [refreshing tokens](https://developer.spotify.com/documentation/web-api/tutorials/refreshing-tokens)
- **Refresh token lifetime**: 6 months from the original login, refreshing does not extend it (new apps from 2026-06-18, existing from 2026-07-20). Expired → `invalid_grant`, log in again. [blog](https://developer.spotify.com/blog/2026-06-18-refresh-token-expiration)
- **No way around the client ID** (2026-10-27): Spotify uses the OAuth Device Authorization Grant for its own TV apps, but a Dashboard app that is not allowlisted gets `unauthorized_client` / "Client not allowed" ([community thread](https://community.spotify.com/t5/Spotify-for-Developers/Device-Authorization-Grant-authentication-flow-for-custom/m-p/5485468), not official docs). The running desktop client offers no API to other programs. The create-app form ([dashboard/create](https://developer.spotify.com/dashboard/create), seen in the user's screenshot): App name, App description (both required), Website (optional), Redirect URIs (type, then «Add»), API/SDK check boxes (Web API), the Developer Terms check box, «Save».
- **Following a playlist** (2026-10-27): the per-type follow endpoints were removed in February 2026; spotipy 2.26 `current_user_follow_playlist` sends `PUT /me/library?uris=spotify:playlist:<id>`. The migration guide says to pass "appropriate scopes" for the saved entities without naming them; the app asks for `user-library-modify` on top of the playlist scopes. Not yet tried live. [migration guide](https://developer.spotify.com/documentation/web-api/tutorials/february-2026-migration-guide), [changelog](https://developer.spotify.com/documentation/web-api/references/changes/february-2026)
- **`show_dialog`**: spotipy's `SpotifyPKCE.get_authorize_url` has no `show_dialog` option (only `SpotifyOAuth` does), so the app appends `&show_dialog=true` itself.
- **Redirect URI**: HTTPS, except loopback IP literals `http://127.0.0.1:PORT` or `http://[::1]:PORT`. `localhost` is not allowed. Exact match; a dynamic port works only for loopback (register without a port). [redirect URIs](https://developer.spotify.com/documentation/web-api/concepts/redirect_uri)
- **Development Mode**: the app owner needs an active Premium subscription (the app stops working if it lapses); up to 5 users per app, each added by name + Spotify email in Dashboard → app → Settings → User Management; users not on the list can log in but get 403. Client IDs per developer: 1 from Feb 2026, 25 from July 2026. Extended Quota Mode: only registered organizations with 250k+ MAU (since 2025-05-15). [quota modes](https://developer.spotify.com/documentation/web-api/concepts/quota-modes), [blog 2026-02-06](https://developer.spotify.com/blog/2026-02-06-update-on-developer-access-and-platform-security)
- **February 2026 Dev Mode changes** (new apps 2026-02-11, existing 2026-03-09) [migration guide](https://developer.spotify.com/documentation/web-api/tutorials/february-2026-migration-guide):
  - `POST /users/{id}/playlists` → `POST /me/playlists`.
  - `/playlists/{id}/tracks` → `/playlists/{id}/items` (GET/POST/PUT/DELETE); playlist field `tracks` → `items`.
  - Playlist contents are returned only for playlists the user owns or collaborates on; others give metadata only.
  - Removed: `GET /users/{id}`, `GET /users/{id}/playlists`, batch `GET /tracks` etc., library writes moved to `/me/library`. `GET /me/tracks` (reading Liked Songs) stays.
  - Track lost `popularity`, `available_markets`, `linked_from`. `external_ids` (ISRC) was listed as removed and then restored. [March 2026 changelog](https://developer.spotify.com/documentation/web-api/references/changes/march-2026)
  - `GET /me` lost `country`, `email`, `product`.
- **Add items**: `POST /playlists/{id}/items`, max 100 URIs per request; scopes `playlist-modify-public` / `playlist-modify-private` (community reports: 403 without `playlist-modify-public`). [reference](https://developer.spotify.com/documentation/web-api/reference/add-items-to-playlist)
- **Playlist visibility**: live 2026-10-28, `POST /me/playlists` with `"public": false` gave `public: true` on a GET right after (scopes included `playlist-modify-private`). Community reports say `public` means "on the profile / in search" and the link still opens the playlist, and some report that a later change does not stick either. The app sends `PUT /playlists/{id}` `{"public": false}` after create; not yet verified live.
- **Search**: `isrc:` filter works for tracks; `limit` max 10 (was 50), default 5; `offset` ≤ 1000; results are limited to the token's account market. Live 2026-10-27: `market=from_token` gives 403 "Insufficient client scope" to a token without `user-read-private`; without `market` the items still carry `is_playable`. [search](https://developer.spotify.com/documentation/web-api/reference/search)
- **429**: quota is shared per endpoint bucket; exceeded → 429, reason `QUOTA_EXCEEDED`, with `Retry-After`.
- **spotipy** 2.26.0 (2026-03-03): `playlist_items` / `playlist_add_items` use `/items`; `current_user_playlist_create` → `/me/playlists`; `user_playlist_create` is deprecated. Its urllib3 retry gives up after 3 tries. [changelog](https://github.com/spotipy-dev/spotipy/blob/master/CHANGELOG.md)

## Yandex Music (no official API)

- Library `yandex-music` 3.2.2 (2026-10-10), Python 3.8–3.14, sync client on `requests[socks]`. 3.2.0 made missing fields `None` with a warning instead of an error; 3.2.2 added `Track.isrc`. [PyPI](https://pypi.org/project/yandex-music/), [changes](https://github.com/MarshalX/yandex-music-api/blob/main/CHANGES.md)
- **Token** [docs](https://ym.marshal.dev/en/main/token.html):
  - Browser: open `https://oauth.yandex.ru/authorize?response_type=token&client_id=23cabbbdc6cd418abb4b39c32c41195d`, log in, allow; the page redirects to `https://music.yandex.ru/#access_token=...&expires_in=...`; copy `access_token` before the next redirect. Lives about a year (`expires_in` ≈ 31.5M s), no refresh.
  - Also: `client.device_auth()` (OAuth device flow, recommended by the library), a bot site, an Android app and browser extensions. Own OAuth apps for Yandex Music cannot be created.
- **Subscriptions** (read from the library, 2026-10-27): someone else's playlists the user follows are their liked playlists, `users_likes_playlists()` → `Like.playlist`; `Playlist.playlist_id` is `"<owner uid>:<kind>"`, the format `users_likes_playlists_add(...)` takes. `users_playlists_list()` returns only the user's own playlists. No cover upload in the library (covers were dropped from the account move).
- **Device flow in 3.2.2** (read from `yandex_music/_client/device_auth.py` on 2026-10-27, worked live 2026-10-28): works on a `Client()` without a token. `request_device_code()` → `POST https://oauth.yandex.ru/device/code` with the Yandex Music Android app's `client_id` (the same one as the browser link above) and a random 10-char `device_id`; returns `DeviceCode(device_code, user_code, verification_url, expires_in, interval)`. `poll_device_token(device_code)` → `POST https://oauth.yandex.ru/token` (`grant_type=device_code` + the built-in client secret); returns `None` while the OAuth error is `authorization_pending`, raises `DeviceAuthError` for any other 400 (`expired_token`, `access_denied`, ...), returns `OAuthToken(access_token, refresh_token, expires_in, token_type)` once confirmed. `device_auth()` wraps both in a loop with `time.sleep(interval)`; the app uses its own loop instead (cancel without waiting out the sleep, no new code on a retry).

## SoundCloud (dropped)

The user dropped SoundCloud on 2026-10-27 because of the first point.

- New API apps can be registered (self-service since May 2026) **only with an Artist Pro subscription**, at `soundcloud.com/you/apps` or via their CLI. [get an API key](https://developers.soundcloud.com/docs/api/register-app), [blog 2026-06-16](https://developers.soundcloud.com/blog/api-credentials-cli-openapi-github/)
- OAuth 2.1 Authorization Code with PKCE required; every client is confidential, so `client_secret` goes in the token request body. Authorize `https://secure.soundcloud.com/authorize`, token `https://secure.soundcloud.com/oauth/token`; access token ~1 h; refresh tokens are single-use. API header `Authorization: OAuth <token>`. Loopback redirects are not mentioned. [API guide](https://developers.soundcloud.com/docs/api/guide)
- Limits per app: ~100 req/min, search 3000/h, likes (incl. listing) 500/24 h; 429 with `Retry-After` when present. [rate limits](https://developers.soundcloud.com/docs/api/rate-limits)
- OpenAPI: Track has `isrc`, `duration` (ms), `access` (`playable`/`preview`/`blocked`); `POST /playlists` takes `tracks: [{urn}]`, `sharing: private`; no documented max. [api.yaml](https://github.com/soundcloud/api/blob/master/openapi/api.yaml)
