# music-transfer: development

## Setup and tests

- Python 3.12, venv at `.venv`. New venv: `python -m venv .venv`, then `.venv\Scripts\python.exe -m pip install -r requirements.txt` (versions are pinned).
- Tests, from the project folder: `.venv\Scripts\python.exe -m pytest -q`. `python -m` puts the project folder on `sys.path`, so there is no `pytest.ini`.
- No-network proof: run the same with `$env:HTTPS_PROXY='http://127.0.0.1:9'`; any accidental HTTPS call fails fast. The login-server tests talk to 127.0.0.1 through `http.client`, which ignores proxies.
- `tests/conftest.py` points `APPDATA` at a temp dir before any import, so tests never touch the real token folder.

## Files on disk

- `config.json` next to the app (`APP_ROOT`: the exe folder when frozen, the project folder otherwise): `{"spotify_client_id": "..."}`. The app writes it (`save_config`, other keys kept) after the first successful Spotify login with an ID typed into the window; nobody has to edit it. Shape: `config.example.json`.
- `%APPDATA%\music-transfer\spotify.json`: spotipy token cache. `yandex.json`: `{"token": "..."}`. The second account of a service (slot 2) uses `spotify-2.json` / `yandex-2.json`. Plain text under the user profile; nothing is written to the project folder.

## Modules (`music_transfer/`)

- `common.py`: paths, `Track`, `Playlist`, `LIKED`, `AppError`, `load_config`, `save_config`, `call_with_retry`.
- `matching.py`: `strip_tags` (search query), `normalize` (comparison), `artist_key` (Cyrillic transliteration), `dedup`, `find_match`.
- `transfer.py`: `Job`, `build_jobs`, `match_jobs`, `copy_jobs` (same service, another account: each playable track is its own match, no search), `write_jobs`, `export_csv`. `progress(done, total)` is called from the worker thread, so the GUI must emit a Qt signal.
- `spotify.py`: `SpotifyService`, login via a local server on port 8765 (PKCE, no client secret). The constructor rejects a client ID that is not 32 hex characters.
- `yandex.py`: `YandexService`, login by OAuth device code (`login`), or by pasting a token as a fallback (`connect`; `TOKEN_URL` is the page that issues one).
- `gui.py`: `Worker` (QThread), `MainWindow`, `run()`. `main.py` only calls `run()`.

Service contract (both services): `name` (the service, also the "same service?" test), `label` (`name · account` once connected), `account`, `account_id`, `connected`, `on_wait`, `restore() -> bool` (cached token, never a browser), `connect(...)`, `disconnect()`, `playlists()` (own ones, then subscriptions with `Playlist.followed`), `tracks(playlist)` (own playlists only), `search(artist, title)`, `search_isrc(isrc)`, `create_playlist(name, tracks) -> id`, `follow(playlist)`. Constructors take `slot` (1, or 2 for a second account: its own token file). Spotify's `restore()` ignores a cached token whose scopes miss one of `SCOPES` (adding `user-library-modify` made everyone log in once); its login URL always carries `show_dialog=true` so Spotify shows whose account it is. Login waits take `stop`, a `threading.Event`, and return `False` when it is set:
- `Spotify.connect(open_url=webbrowser.open, stop=None) -> bool` blocks up to 3 minutes; `stop` is checked every second (the loopback server's `timeout`).
- `Yandex.login(on_code, stop, open_url=webbrowser.open) -> bool`: requests a device code, calls `on_code(user_code, verification_url)` (worker thread), opens the page, polls every `interval` s via `stop.wait` until confirmed or `expires_in` runs out, then `connect`s with the token (saved as before). OAuth errors become `AppError` naming `oauth.yandex.ru`.
- `Yandex.connect(token_text)` takes a bare token or the whole redirect URL. Services and their HTTP sessions are not thread-safe: one worker at a time per service.

## GUI

- Run: `.venv\Scripts\python.exe main.py`. Try it with a temp `APPDATA` so the real token folder stays untouched. The user's own launcher is `run.bat` (tests, then the app in a console, real `APPDATA`); it checks `%errorlevel% neq 0`, because `if errorlevel 1` misses the negative exit code of a Qt crash.
- All network work goes through `MainWindow._run`: one `Worker` at a time, the central widget is disabled while it runs (progress and status live in the status bar). Functions passed to `_run` run in the worker thread and never touch widgets; results come back through signals connected to bound methods of the window. `_run` calls `wait()` on the previous worker before replacing it.
- Closing the window during a run asks first, then `os._exit(1)`: a running `QThread` at interpreter exit aborts the process, and the core has no cancel (see the shared `C:\Users\theme\.claude\docs\pyside6.md`).
- Any change of selection, mode, source, target or account drops the match results (`_invalidate`); «Перенести» is enabled only after a match with unwritten jobs. The merged playlist name is read at write time, not at match time. After a transfer the table shows the per-playlist summary; not-found tracks stay available through the CSV button.
- Services are created from `config.json` in `MainWindow.__init__`. Without a client ID (or with a broken config, whose error is shown in the hint) the Spotify row shows a Client ID field and a hint (Dashboard link, Redirect URI, User Management); «Войти» validates the ID, logs in with a fresh `SpotifyService`, and only after a successful login adds it to `services` and saves the ID. A wrong ID therefore never gets saved. Startup tries `restore()` for each service in the worker.
- Getting a client ID: the hint's link opens `SpotifyGuide`, a non-modal always-on-top dialog with a button to the Dashboard's create page (`CREATE_APP_URL`) and the form's values (`APP_FORM`: App name, App description, Redirect URIs) with «Копировать» buttons. While Spotify is not set up, `_clipboard_changed` (on `QClipboard.dataChanged`, which also fires for copies made in the browser) puts any copied 32-hex string into the Client ID field and closes the guide; it never logs in by itself.
- Moving to a second account: «+ второй аккаунт Spotify / Яндекса» (shown once the first account of that service is connected) reveals a slot-2 row; for Spotify it also opens `SecondAccountGuide` (link and button to the Dashboard: the second account must be in the app's User Management, the client ID is shared), which the row's «как подключить второй аккаунт Spotify» link reopens and a successful login closes. Logging it into the same account as the first one is refused (`account_id` match) and its token dropped. «Откуда / Куда» hold the service objects (`itemData`), shown by `label`. When both are the same service, «Найти треки» copies (`copy_jobs`) instead of searching, and subscriptions appear in the playlist list under a header («Выбрать все» skips them; they are hidden, so never picked, for another service). «Перенести» writes the playlists, then follows the ticked subscriptions. The name field in «По плейлистам» names the playlist made from the liked tracks (optional); in «В один плейлист» it names the merged one.
- Login waits go through `MainWindow._login`: `_run(..., stop=Event)` shows «Отмена» in the status bar, which sets the event. Long runs (find, transfer) still have no cancel.
- Yandex «Войти» runs the device flow unless the token field (behind «Другой способ: вставить токен») is shown and filled. The code arrives through the `code_ready` signal (emitted in the worker, queued to the window): it is copied to the clipboard and shown in the status bar with a link to the page.
- Look: `theme.py`, a dark theme in Spotify colours (Fusion + dark palette + one app-level stylesheet); `run()` applies it and darkens the native title bar through DWM (attributes 20 and 35, both `S_OK` on this PC). Widgets are styled by object name (`backdrop` for the green glow, `card`, `title`, `hint`) and by dynamic properties switched with `_restyle`: `accent` (a green button is the next thing to press: «Войти» until connected, «Найти треки», «Перенести») and `on` (a green status). No inline `setStyleSheet`: it cuts the widget's children off the app-level rules. The check box and combo arrow icons are `assets/*.svg`, loaded by absolute path. Tests run without the theme; for screenshots call `theme.apply(app)` before creating the window.
- `tests/test_gui.py` runs the window offscreen with fake services (`QT_QPA_PLATFORM=offscreen`, `QT_QPA_FONTDIR=C:\Windows\Fonts`; both set at the top of the file). The fakes record whether each network-like call ran on the main thread. A screenshot check (`QWidget.grab().save(...)`) needs the same env vars and `QApplication.setFont(QFont("Segoe UI", 9))`, otherwise Latin text renders in a pixel font.

## Build (milestone 5)

`powershell -ExecutionPolicy Bypass -File build.ps1` → `dist\MusicTransfer-Setup-<version>.exe` (one file, ~36 MB; the app folder is ~117 MB). Steps: offline tests (no build if they fail), PyInstaller into `dist\MusicTransfer\` (spec in `build\`), Inno Setup with `installer.iss`. `build\` and `dist\` are build output, ignored by git. Version: `__version__` in `music_transfer\__init__.py` (one place: `build.ps1` passes it to ISCC as `/DAppVersion`, `release.ps1` tags `v<version>`, the window title shows it).

- Inno Setup 6.7.3, installed per user with `winget install --id JRSoftware.InnoSetup -e --scope user` (`%LOCALAPPDATA%\Programs\Inno Setup 6\ISCC.exe`). `installer.iss` and `build.ps1` are UTF-8 with BOM (Cyrillic: Windows PowerShell 5.1 and ISCC read files without BOM as ANSI). Keep `AppId` as it is: upgrades and uninstall find the installed copy by it.
- The installer is per user, no admin: `{autopf}` = `%LOCALAPPDATA%\Programs\Music Transfer`, where the app can write `config.json`. It ships the project's `config.json` (the owner's client ID; friends only press «Войти», each must be in the app's User Management) with `onlyifdoesntexist`, so an upgrade keeps the installed one; uninstall removes it too, logins in `%APPDATA%\music-transfer` stay. Start-menu shortcut, optional desktop shortcut, «Запустить» at the end.
- PyInstaller (from the `pyside6-desktop` skill, checked here): `--onedir`, not `--onefile` (onefile is flagged by antivirus more often; the installer is the single file); `--windowed`; run from the project root, which has no `__init__.py` (Qt DLL loading breaks otherwise); `--python-option "X utf8"` (not `--runtime-option`, which 6.22.3 lacks) — a probe build printed `sys.flags.utf8_mode` = 1; `--add-data <abs>\music_transfer\assets;music_transfer/assets` with an absolute source, because `--specpath build` makes relative ones resolve against `build\`.
- No UPX (not installed), no code signing (paid certificate): SmartScreen shows «Windows защитил ваш компьютер» on a downloaded setup — «Подробнее → Выполнить в любом случае». No friends' guide yet.
- Checked on 2026-10-27: no missing-module warnings for our packages, `requests`, `charset_normalizer`, `urllib3`, `idna`, `certifi`; the theme icons and `imageformats\qsvg.dll` are in the bundle; the built exe and the installed one start (offscreen, temp `APPDATA`); a silent install to a temp folder (`/VERYSILENT /DIR=... /NOICONS /TASKS=""`) and `unins000.exe /VERYSILENT` left no folder and no uninstall registry key. Not checked: network calls from the frozen exe (the first live login in it does that), the window on screen.
- No `ThreadPoolExecutor`, no inline `setStyleSheet` (the theme is app-level), no dynamic widget deletion in the GUI, so the skill's pool-signal and `deleteLater` rules and its inline-QSS rules do not apply today.

## Updates and releases

- The repository is public on GitHub (`REPO` in `music_transfer\update.py`), so friends' copies can download updates without logging in. `.gitignore` keeps out `config.json` (the client ID; it still ships inside the public installer, which is fine: Dev Mode only lets listed users in) and `build-prompt.md` (personal context). Commits use a repo-local noreply `user.email`.
- «Проверить обновление» (status bar): `update.latest()` asks `api.github.com/repos/<REPO>/releases/latest` (no login; 60 requests an hour per IP) and accepts only a `MusicTransfer-Setup-<v>.exe` under `https://github.com/<REPO>/releases/download/`. If it is newer (versions compare as numbers) and the app is the installed build, it asks once, downloads to `%TEMP%`, checks the size and the SHA-256 the API gives as `digest`, runs the installer with `/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /CLOSEAPPLICATIONS /UPDATE=1` and quits; `installer.iss` starts the new version when `/UPDATE=1` is set (`[Run]` with `Check: IsUpdate`). Run from sources, the button only reports a newer version.
- Releasing (the user runs it; Claude never pushes): `gh auth login` once (GitHub CLI 2.103, winget). For each version: raise `__version__`, add `docs\changelog.md`, commit, `powershell -ExecutionPolicy Bypass -File release.ps1`. It checks that the logged-in account owns `REPO`, a clean tree and a new tag; runs `build.ps1`; creates the public repo on the first run; pushes the branch and `v<version>`; `gh release create` with the setup.exe.
- Published: https://github.com/takeshilp/music-transfer (public, branch `main`), release `v0.2.0` on 2026-10-27 via `release.ps1` (git uses gh's credentials after `gh auth setup-git`). Checked live: `update.latest()` returns `0.2.0` with a `digest` on the asset, and `update.download()` saved a file identical to the local build. End to end on 2026-10-28: installed 0.2.0 → «Проверить обновление» → «Yes» → `MusicTransfer-Setup-0.2.1.exe` downloaded to `%TEMP%`, installed silently, the new version started 13 s later (registry `DisplayVersion` 0.2.1); no SmartScreen prompt. The downloaded installer stays in `%TEMP%` (it cannot delete itself while running): `update.cleanup()` removes `MusicTransfer-Setup-*.exe` there at the next start.

## Conventions

- Every API call goes through the service `_call`, which wraps `call_with_retry`: it waits out 429 (`Retry-After`, 5 s default, more than 300 s is an error) and turns network failures into `AppError` that names the host.
- `on_wait(host, seconds)` (an attribute on each service, `None` by default, also a `call_with_retry` argument) is called before each wait (a 429, and read retries after a masked Spotify 5xx), so the GUI shows "Ожидание <host>: N с" instead of looking frozen.
- Only `AppError` text (Russian) reaches the user. Other exceptions are mapped in `_call`.
- Never enable DEBUG logging: spotipy then logs `Authorization: Bearer ...` (client.py) and the token-endpoint body with `refresh_token` / `code_verifier` (oauth2.py). "No tokens in logs" holds only while DEBUG is off, and the app has no log file.
- Writes (`create_playlist`, add items) go through `_call(..., write=True)`: a headerless 429 "Max Retries" (spotipy's disguise for an exhausted 5xx) is not repeated for them, so no duplicate playlists or track batches. Reads retry it, then report "временно недоступен". `write_jobs` skips jobs that already have `added`, so re-running after a failure continues instead of recreating.
- Batch sizes: Spotify add 100, read 50, search 10; Yandex insert 100, fetch 500.
- Known limits get a comment `# shortcut: <limit>, <when to upgrade>`.
- Matching: ISRC first, then artist + normalized title + duration within 5 s. "(with X)" is dropped like "feat."; "По плейлистам" mirrors source duplicates, only "В один плейлист" dedups.
- Spotify login server: `allow_reuse_address = False` (on Windows SO_REUSEADDR lets a second process bind the same port, so the busy-port check would never fire), handler `timeout = 5`, silent `log_message`.
- `_PKCE.get_authorization_code` raises: spotipy's own fallback would start a blocking server or call `input()`.
